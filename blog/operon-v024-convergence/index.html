Operon v0.24: Why Your Agent Framework Needs a Structural Linter

A source-agnostic IR for five agent frameworks, four TLA+ protocol specs, and co-design convergence

Bogdan Banu · March 2026 · github.com/coredipper/operon

Release: v0.24.0
Abstract

Multi-agent orchestration is split across incompatible frameworks (Swarms, DeerFlow, AnimaWorks, Ralph, A-Evolve, among others), each with its own coordination primitives. Beneath those APIs, they share the same structural failure modes: error amplification in deep chains, sequential handoff overhead, and tool-density coordination tax. Operon v0.24 introduces a source-agnostic structural linter that checks any framework’s agent topology for these risks before deployment, alongside four TLA+ formal specifications for its coordination protocols.

1. Framework Fragmentation

The ACG survey catalogs over forty multi-agent coordination methods. Most reinvent the same underlying patterns (supervisor hierarchies, sequential pipelines, parallel fan-out) under incompatible names, APIs, and failure modes, leaving no shared vocabulary for judging whether a topology will amplify errors or accumulate coordination overhead.

As Evans et al. argue in their work on collective intelligence, different problem shapes call for different coordination patterns, so expecting a single framework to replace the rest is unrealistic. Interoperation is more practical, and it requires a shared structural language that describes a topology independently of whichever framework instantiated it.

Without that shared layer, teams discover topology bugs only after deployment. A Swarms HierarchicalSwarm with eight agents in a deep delegation chain can carry a 6.4x error amplification bound with no warning before production. A DeerFlow LangGraph session with twelve sequential handoffs can spend 40% of its wall-clock time on coordination overhead while the runtime reports nothing amiss. Both outcomes follow directly from the graph structure, regardless of the prompts or models inside each node.

Static Topology Checks

Error amplification, sequential penalty, and tool-density tax are properties of the coordination graph itself. Because they depend on topology rather than runtime behavior, they can be checked statically before making a single LLM call.

2. ExternalTopology as a Shared IR

Operon v0.24 introduces ExternalTopology, a frozen dataclass that any framework’s configuration can be parsed into. It holds only the structural data needed for analysis (agent names, roles, directed edges, and metadata) and imports nothing from the source framework. 

@dataclass(frozen=True)
class ExternalTopology:
    source: str              # "swarms", "deerflow", "animaworks", "ralph", "aevolve"
    pattern_name: str        # e.g., "HierarchicalSwarm", "LangGraphSession"
    agents: tuple[dict, ...]  # at least "name" and "role" per agent
    edges: tuple[tuple[str, str], ...]  # directed (from, to) pairs
    metadata: dict = field(default_factory=dict)

The main entry point is analyze_external_topology(), which takes any ExternalTopology and applies Operon’s four epistemic theorems as a structural linter:

  1. Error amplification bound: upper bound on how far errors can compound across the topology.
  2. Sequential penalty: estimated wall-clock overhead introduced by sequential handoffs.
  3. Tool density: planning-cost ratio across the assigned tool set.
  4. Topology classification: comparison between the parsed topology and Operon’s recommendation for the detected task shape.

For example, analyzing a Swarms HierarchicalSwarm: 

from operon_ai.convergence import (
    parse_swarm_topology,
    analyze_external_topology,
)

# Parse a Swarms HierarchicalSwarm config
topology = parse_swarm_topology(
    pattern_name="HierarchicalSwarm",
    agent_specs=[
        {"name": "director", "role": "supervisor", "capabilities": ["planning"]},
        {"name": "researcher", "role": "worker", "capabilities": ["web_search"]},
        {"name": "writer", "role": "worker", "capabilities": ["text_gen"]},
        {"name": "reviewer", "role": "critic", "capabilities": ["code_review"]},
    ],
    edges=[
        ("director", "researcher"),
        ("director", "writer"),
        ("researcher", "reviewer"),
        ("writer", "reviewer"),
    ],
)

# Analyze with Operon's epistemic theorems
result = analyze_external_topology(topology)

print(f"Risk score: {result.risk_score}")        # 0.0 - 1.0
print(f"Warnings: {result.warnings}")             # structural concerns
print(f"Recommended: {result.topology_advice}")   # Operon's suggestion
print(f"Template: {result.suggested_template}")   # ready for PatternLibrary

The call returns an AdapterResult with a composite risk score, structural warnings, a topology recommendation, and a PatternTemplate ready to register in a PatternLibrary. Because the adapter works exclusively on dicts and tuples, it never imports the swarms package.

3. Five Framework Adapters

v0.24 ships adapters for five agent orchestration frameworks, each built around a different coordination model:

Framework Coordination Model Parser What Operon Adds
Swarms Graph-based workflows parse_swarm_topology() Error amplification analysis, topology mismatch detection
DeerFlow LangGraph state machines parse_deerflow_session() Sequential penalty detection, skill-to-template bridging
AnimaWorks Supervisor hierarchies parse_animaworks_org() Role-to-stage mapping, memory bridge integration
Ralph Event-driven hats parse_ralph_config() Backpressure analysis, hat-to-stage conversion
A-Evolve Evolutionary workspaces parse_aevolve_workspace() Skill import, evolution gating, monotonic score verification

Every adapter follows the same pattern: parse the framework-specific configuration into an ExternalTopology, then call analyze_external_topology(). The analysis code does not know or care which framework produced the topology. Adding a sixth adapter is approximately 100 lines of parsing code.

Each adapter also includes a source-specific converter (swarm_to_template(), deerflow_to_template(), ralph_to_template(), animaworks_to_template(), aevolve_to_template()) that builds a PatternTemplate while preserving framework-specific metadata. Those templates can be registered in a PatternLibrary and exchanged between organisms using the social learning protocol.

4. Formal Verification: TLA+ for Agent Systems

Static linting catches topology-level risks, while concurrency properties require checking across execution histories: whether template exchange always respects developmental stage requirements, whether a closed critical period can ever reopen, and whether a non-converging organism is guaranteed to halt. Answering those questions across every possible interleaving of concurrent actions requires formal verification.

What is TLA+?

TLA+ (Temporal Logic of Actions) is Leslie Lamport’s specification language for concurrent and distributed systems. You model a system as a state machine (an initial state and a set of transition actions) and specify invariants and temporal properties that must hold over all reachable states. The TLC model checker then exhaustively explores the state space to verify those properties.

It is used in production systems where concurrency bugs are costly: Amazon uses TLA+ for AWS infrastructure protocols, Microsoft for Azure Cosmos DB’s consistency guarantees, and MongoDB for its replication protocol. Finite test suites only cover the interleavings you happen to write tests for, so subtle timing-dependent bugs slip past them.

Concurrency in agent coordination

Multi-agent orchestration involves the same concurrency hazards as any distributed system. Importing a template from organism B into organism A couples trust scoring, stage verification, and library updates into a shared state transition. A watcher checking convergence while stages are still executing performs a concurrent safety check, and A-Evolve accepting a mutation while another organism reads the workspace creates a standard read-write race.

Unit and integration tests exercise whichever action orders you thought to script, whereas TLC checks every interleaving within the model bounds, including cases where three organisms attempt template exchange while one advances a developmental stage. Those rare orderings are usually the ones behind irreproducible failures in production.

Protocol-Level Verification

Agent orchestration protocols share the concurrency failure modes of distributed databases and cloud infrastructure, so checking them with the same model-checking tools catches protocol flaws before they reach code.

What Operon’s specs verify

Operon ships four TLA+ specifications in the specs/ directory. Each models a specific coordination protocol and proves that its safety invariants hold for all possible interleavings.

1. TemplateExchangeProtocol.tla

Models the social learning protocol from operon_ai/coordination/social_learning.py. Organisms maintain pattern libraries, exchange templates with peers, and modulate adoption via EMA-based trust scoring (epistemic vigilance). The biological analogy is horizontal gene transfer in bacteria.

Safety invariant S1 (TemplateAdoptionSafety): An adopted template’s minimum stage requirement never exceeds the adopter’s current developmental stage. An organism in the JUVENILE stage cannot import a template requiring MATURE capabilities under any concurrent sequence of exports, imports, and stage advances by other organisms.

Safety invariant S2 (TrustMonotonicity): Trust is only modified through the RecordOutcome action, which updates trust via exponential moving average. Export, Import, and StageAdvance all leave trust unchanged. Trust cannot be manipulated by any action other than recorded outcomes. 

\* From TemplateExchangeProtocol.tla -- the stage guard
Import(org, peer) ==
    /\ org # peer                                    \* No self-adoption
    /\ trust[org][peer] >= MIN_TRUST                 \* Trust guard
    /\ \E tmpl \in exported[peer] :
         /\ tmpl \notin library[org]                 \* Not already held
         /\ StageGEQ(stage[org], MinStage[tmpl])     \* Stage guard
         /\ MeetsAdoptionThreshold(peer, tmpl, trust[org][peer])
         /\ library' = [library EXCEPT ![org] = library[org] \union {tmpl}]

2. DevelopmentalGating.tla

Models the developmental staging protocol from operon_ai/state/development.py. Organisms consume telomere capacity over time, advancing through four stages (EMBRYONIC, JUVENILE, ADOLESCENT, MATURE). Critical periods open and close permanently, mirroring neurodevelopmental critical periods (bounded windows of high plasticity for language acquisition or imprinting).

Safety invariant S2 (CriticalPeriodIrreversibility): Once a critical period closes, it never reopens; periods only move forward from pending to open to closed. After an organism closes its “rapid learning” window, no combination of concurrent ticks, scaffolding from peers, or tool acquisitions can reopen it.

Safety invariant S3 (StageMonotonicity): Developmental stages never regress. An organism that has reached ADOLESCENT cannot return to JUVENILE. This is a temporal property verified across all state transitions.

3. ConvergenceDetection.tla

Models the watcher convergence protocol from operon_ai/patterns/watcher.py. Organisms execute stages and may receive interventions (RETRY, ESCALATE, HALT). When the ratio of interventions to observed stages exceeds a threshold, the organism is halted. This follows Hao et al.’s BIGMAS framework, which uses intervention count as a convergence proxy.

Safety invariant S1 (HaltIsTerminal): Once halted, no more stages or interventions occur. Halt is irreversible and immediate.

Liveness property (BoundedNonConvergence): If an organism’s intervention rate exceeds the threshold, it is eventually halted regardless of what other agents do concurrently. The system cannot remain indefinitely in a state above the threshold without halting.

4. EvolutionGating.tla

Models the A-Evolve Solve → Observe → Evolve → Gate → Reload loop. Organisms maintain a workspace version and a benchmark score. Mutations are generated nondeterministically; a gate action accepts the mutation only when the new score meets or exceeds the current score. Rejected mutations are rolled back. The analogy is positive selection in directed evolution.

Safety invariant S1 (MonotonicScore): The score never decreases after an accepted mutation. If the workspace version advances, the new score is at least as high as the old score. A-Evolve’s git-based rollback guarantees monotonic improvement.

Safety invariant S2 (GateBeforeDeploy): Workspace versions only increment by passing through the gate, never jumping ahead or decrementing. Every version change is preceded by a fitness check, so unvalidated mutations cannot reach the workspace.

How TLC model checking works

TLC works by exhaustive state exploration. Given a finite model (for example, 2 organisms, 3 templates, and 5 telomere units), it visits every state reachable from the initial configuration. For TemplateExchangeProtocol with 2 organisms and 3 templates, that covers every interleaving of Export, Import, RecordOutcome, and StageAdvance actions across both organisms.

Whenever a reachable state violates an invariant, TLC outputs a counterexample trace showing the exact sequence of actions that triggered the failure, which makes protocol bugs much easier to diagnose and fix.

All four Operon specs pass TLC on their configured finite models, with every safety invariant and temporal property holding across all explored states.

The gap between model and reality

TLA+ verifies the model rather than the Python implementation. The specs abstract away wall-clock timing, network failures, floating-point precision, and Python’s GIL. TemplateExchangeProtocol models trust as a real number in [0, 1], whereas the implementation uses IEEE 754 doubles; ConvergenceDetection models intervention rate as exact rational division, whereas the code uses floating-point comparisons.

Those abstractions are deliberate and documented. Model checking targets protocol-level defects: missing guards, broken state transitions, and unexpected interleavings across concurrent organisms that finite tests rarely trigger.

The specs live in specs/ in the Operon repository: TemplateExchangeProtocol.tla, DevelopmentalGating.tla, ConvergenceDetection.tla, EvolutionGating.tla.

5. Co-Design Convergence: Does the Adaptive Loop Stabilize?

Chaining the five adapters inside an adaptive assembly loop (run a topology, score its performance, select a better template, repeat) raises a composition question: does the loop converge, or can it oscillate indefinitely between configurations?

Zardini’s co-design theory from ETH Zurich applies directly here. In the co-design framework, each adapter is a design problem (DP): a monotone map from a resource poset (inputs, constraints) to a functionality poset (outputs, capabilities), where monotonicity means more resources yield at least as many functionalities. 

from operon_ai.convergence import (
    DesignProblem,
    compose_series,
    compose_parallel,
    feedback_fixed_point,
)

# Each adapter as a design problem
swarms_dp = DesignProblem(
    name="swarms_adapter",
    evaluate_fn=lambda r: {"risk": analyze_swarms(r), "templates": r["templates"] + 1},
    feasibility_fn=lambda r: r.get("agents", 0) > 0,
)

deerflow_dp = DesignProblem(
    name="deerflow_adapter",
    evaluate_fn=lambda r: {"risk": analyze_deerflow(r), "skills": r.get("skills", 0)},
    feasibility_fn=lambda r: r.get("session") is not None,
)

# Series composition: swarms analysis feeds deerflow analysis
pipeline = compose_series(swarms_dp, deerflow_dp, name="swarms_then_deerflow")

# Feedback fixed-point: does the adaptive loop converge?
final_state, iterations, converged = feedback_fixed_point(
    pipeline,
    initial={"agents": 4, "templates": 0, "session": True, "skills": 0},
    convergence_key="risk",
    epsilon=0.01,
    max_iterations=100,
)

print(f"Converged: {converged} in {iterations} iterations")
print(f"Final risk: {final_state['risk']}")

The adaptive assembly loop (run → score → select → repeat) is feedback composition in Zardini’s framework. The monotone convergence theorem guarantees that if the scoring function is monotone and bounded, the sequence of scores approaches a limit. feedback_fixed_point() provides practical epsilon-approximate termination: when the score changes by less than epsilon between iterations, the loop halts.

Preventing Oscillation

Without a convergence guarantee, an adaptive assembly loop can cycle indefinitely: template A scores higher than B in context X, B scores higher in context Y, and switching templates flips the context. Co-design theory gives the conditions under which a monotone, bounded scoring function avoids that cycle.

6. Integrating with External Frameworks

If you are building an agent framework, Operon can serve as a structural linter with a lightweight integration boundary:

  • No runtime coupling: Adapters take plain dicts and tuples across a serialization boundary, so Operon never imports your framework and your framework never has to import Operon at runtime.
  • Static analysis out of the box: Parsing a config into an ExternalTopology and passing it to analyze_external_topology() yields error amplification bounds, sequential penalty estimates, tool density ratios, and topology recommendations without building that analysis yourself.
  • Portable templates: Because every adapter emits standard PatternTemplate objects, a template extracted from a Swarms workflow can be registered in a PatternLibrary and reused by organisms running DeerFlow sessions.
  • Small adapter surface: ExternalTopology only needs agent names, roles, and directed edges, so adding support for another framework takes roughly 100 lines of parsing code on top of the same source-agnostic analyzer.

The convergence adapters also include catalog-seeding functions (seed_library_from_swarms(), seed_library_from_deerflow(), seed_library_from_ralph()) that populate a PatternLibrary with pre-analyzed templates from each framework’s standard workflow patterns, giving the adaptive assembly loop a baseline catalog to start from.

7. Roadmap

v0.24 completes the convergence adapter layer (phases C1 through C4). The next phases cover:

  • C5: Compilers. Reverse the direction by compiling Operon organisms back into Swarms, DeerFlow, and Ralph configurations via organism_to_swarms(), organism_to_deerflow(), and organism_to_ralph() (currently in design).
  • C6: Cross-target evaluation. Run the same organism blueprint against A-Evolve benchmarks across all five frameworks and compare structural predictions against empirical performance.
  • C7: DSPy-style prompt optimization. Use A-Evolve’s evolution loop to optimize prompts within Operon organisms, with the evolution gating spec ensuring monotonic improvement.

The convergence paper documenting the formal framework and proofs is available at article/paper2/main.pdf.

8. Closing

Rather than consolidating on a single orchestration framework, multi-agent systems benefit from a shared structural layer for analyzing coordination graphs. v0.24 puts three pieces of that layer in place: five adapters showing that one IR covers graph-based, event-driven, and evolutionary frameworks; four TLA+ specifications verifying protocol safety across concurrent interleavings; and a co-design convergence formulation bounding the adaptive assembly loop.

The structural linter, zero-coupling adapters, and TLA+ specs are all open source and ready to run against any framework’s workflow configuration before deployment.
