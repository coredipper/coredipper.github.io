Operon v0.18: Pattern-First Skills

Skill Organisms, Provider-Bound Agents, and a Thinner Front Door for Multi-Agent Workflows

Bogdan Banu · March 2026 · github.com/coredipper/operon

Release: v0.18.0
Abstract

v0.17 turned operon into a language for reasoning about agent architecture. v0.18 focuses on usability: exposing common workflows up front so engineers do not have to learn the formal substrate before writing code. The release adds a pattern-first API, a provider-bound skill runtime that mixes deterministic stages with fast and deep models, and a small component interface for attaching telemetry without rewriting the workflow. In retrospect, the smaller v0.16 provider work turned out to be essential here as well, since binding stages to real providers is what makes the new runtime practical.

1. What Felt Missing After v0.17

The strongest feedback I got after the epistemic release was also the fairest: operon still exposed too much of its formal vocabulary directly. I like that vocabulary because it keeps the architecture precise, but most engineers do not want to start from optics, coalgebras, or epistemic partitions. They want to know whether a workflow is safer, cheaper, easier to inspect, or easier to reconfigure.

That feedback pushed v0.18 in a more practical direction. The release puts a thinner public API on top of the existing machinery, letting you start from a concrete workflow pattern and inspect the underlying structure only when you need it.

Design Goal

Keep the formal machinery intact, without requiring it up front.

2. The Pattern-First API

The first part of v0.18 is a new public layer in operon_ai.patterns. It adds three simpler entry points:

  • advise_topology(...) for architecture guidance from task shape, tool count, and error tolerance.
  • reviewer_gate(...) for the common one-worker-plus-reviewer pattern.
  • specialist_swarm(...) for centralized specialist decomposition.
from operon_ai import advise_topology, reviewer_gate, specialist_swarm

advice = advise_topology(
    task_shape="sequential",
    tool_count=2,
    subtask_count=3,
    error_tolerance=0.02,
)

gate = reviewer_gate(
    executor=lambda prompt: f"EXECUTE: {prompt}",
    reviewer=lambda prompt, candidate: "safe" in prompt.lower(),
)

swarm = specialist_swarm(
    roles=["legal", "security", "finance"],
    workers={...},
)

These wrappers still construct the same formal objects underneath and expose both .diagram and .analysis, so you get the full epistemic machinery whenever you inspect them.

Reference Implementation: operon_ai/patterns/advisor.py, operon_ai/patterns/review.py, operon_ai/patterns/swarm.py

3. Skill Organisms

The main addition in v0.18 is a runtime for multi-stage skills, structured more like a small organism than a single prompt wrapper. Each stage can be a deterministic Python handler, a fast model bound to fixed classification work, or a deeper model handling open-ended planning.

flowchart LR U[Task] I[Intake
deterministic] R[Router
fast / cheap] P[Planner
deep / fuzzy] T[TelemetryProbe] U --> I --> R --> P I -. events .-> T R -. events .-> T P -. events .-> T

skill_organism(...), SkillStage, and TelemetryProbe put model selection into the workflow definition itself, keeping it out of ad-hoc wrapper scripts. 

from operon_ai import MockProvider, Nucleus, SkillStage, TelemetryProbe, skill_organism

fast = Nucleus(provider=MockProvider(...))
deep = Nucleus(provider=MockProvider(...))
telemetry = TelemetryProbe()

organism = skill_organism(
    stages=[
        SkillStage(name="intake", role="Normalizer", handler=lambda task: {"request": task}),
        SkillStage(name="router", role="Classifier", instructions="Return a deterministic routing label.", mode="fixed"),
        SkillStage(name="planner", role="Planner", instructions="Use the routing result to propose the next action.", mode="fuzzy"),
    ],
    fast_nucleus=fast,
    deep_nucleus=deep,
    components=[telemetry],
)

result = organism.run("Customer says the refund never posted.")

Separating stages from attached components lets you add telemetry, review gates, or health checks without rewriting the skill itself, while keeping the public API straightforward to call.

Reference Implementation: operon_ai/patterns/organism.py, examples/69_skill_organism_runtime.py

4. Why v0.16 Matters in Retrospect

It is worth mentioning v0.16 here, even though it was a smaller release without its own write-up. It added an OpenAI-compatible provider path and made the Nucleus layer easier to run across different backends.

At the time that looked like routine integration plumbing, but in retrospect it made v0.18 possible: the skill runtime is only practical because stages can bind to real provider-backed nuclei instead of the older pedagogical BioAgent mock path.

How v0.16, v0.17, and v0.18 Fit Together

v0.16 made the provider layer usable across real backends, v0.17 made the architecture analysis explicit, and v0.18 combines both into an API engineers can build on directly.

5. Examples and Spaces

The release adds two practical entry points to the examples:

  • examples/68_pattern_first_api.py for the new thin wrappers.
  • examples/69_skill_organism_runtime.py for provider-bound, multi-model skills.

I also retuned the two epistemic Hugging Face Spaces around this more practical entry path. The Epistemic Space now leads with a Pattern Advisor, and the Diagram Builder now starts from useful presets like reviewer gate and specialist swarm instead of making people type raw diagrams first.

Reference Implementation: operon-epistemic, operon-diagram-builder

7. Separating Internals from Ergonomics

More important than the three helper functions themselves is the boundary v0.18 starts drawing between operon’s formal internals and its public API.

That separation is necessary if the framework is going to be useful beyond the small group of people, myself included, who enjoy the formal model for its own sake. The categorical structure and the epistemic analysis are still there underneath, but the library should be easy to use in a real workflow before anyone has to care about the mathematics.
