Operon v0.19: Bi-Temporal Memory

Append-Only Facts, Dual Time Axes, and Belief-State Reconstruction for Auditable Agent Systems

Bogdan Banu · March 2026 · github.com/coredipper/operon

Release: v0.19.0
Abstract

v0.18 simplified operon’s public API. v0.19 works lower in the stack, adding a memory subsystem that tracks both when a fact became true in the world and when the system learned about it. Conflating those two timestamps causes a recurring class of bugs whenever an agent ingests delayed or retroactively corrected data. The new BiTemporalMemory is append-only: corrections close old records and append new ones, so any past belief state can always be reconstructed. That gives compliance auditing, temporal queries, and agent self-inspection a clean data model to build on.

1. The Problem with a Single Timestamp

Most agent memory systems stamp each fact with a single time: when it was stored. That works as long as the system learns about events the moment they happen, which rarely holds in practice.

A client’s risk tier changes on Monday. The CRM sync runs on Wednesday. A manual review on Friday discovers the tier should have been “high,” not “medium.” Now three different moments are in play, and a single timestamp cannot distinguish between them.

Delayed ingestion and retroactive corrections are routine in compliance, healthcare, and finance. For agents operating in those domains, “what did the system believe when it made that decision?” and “what is true now?” are two separate questions.

Valid Time vs. Record Time

Valid time is when a fact holds in the world. Record time is when the system learned about it. The two diverge whenever information arrives late or gets corrected, and an agent that conflates them cannot reconstruct why it acted as it did.

2. Bi-Temporal Data in Databases

Bi-temporal modeling goes back decades: Snodgrass formalized it in the 1990s, and SQL:2011 standardized temporal tables with PERIOD FOR and AS OF queries. Operon brings the same two-axis model directly into the agent memory layer, where valid time and record time govern what an agent can retrieve at any given point.

Operon’s implementation is an in-memory, append-only store with no database dependency. It gives agent workflows temporal retrieval semantics directly in Python, without requiring external infrastructure.

3. The Data Model

A BiTemporalFact is a frozen dataclass with two time intervals: 

BiTemporalFact(
    fact_id="a1b2c3d4",
    subject="client:42",
    predicate="risk_tier",
    value="medium",
    valid_from=day1,       # when the fact became true in the world
    valid_to=None,         # None = still true (open-ended)
    recorded_from=day3,    # when the system ingested it
    recorded_to=None,      # None = currently active record
    source="crm",
    confidence=1.0,
    tags=(),
    supersedes=None,       # points to the fact this corrects
)

Unlike the mutable dataclasses used elsewhere in operon’s memory layer, BiTemporalFact is frozen. In an append-only store, corrections insert new records rather than editing existing ones, so immutability directly enforces the storage contract.

4. Write Semantics: Record and Correct

The store exposes two write operations: record_fact() appends a new fact, and correct_fact() closes an existing record by setting its recorded_to timestamp before appending a replacement whose supersedes field points back to the original. 

from operon_ai import BiTemporalMemory

mem = BiTemporalMemory()

# Day 1: risk tier becomes "medium" in the world
# Day 3: system ingests it
fact = mem.record_fact("client:42", "risk_tier", "medium",
                       valid_from=day1, recorded_from=day3, source="crm")

# Day 5: manual review corrects to "high", retroactive to day 1
correction = mem.correct_fact(fact.fact_id, "high",
                              valid_from=day1, recorded_from=day5,
                              source="manual_review")

The old record stays in the store with its recorded_to set to the correction time, closing it on the record-time axis. The replacement gets a fresh fact_id and an open recorded_to. Keeping both records is what makes past belief states reconstructible.

Why Append-Only

Mutating facts in place destroys the state the agent actually saw at decision time. Keeping writes append-only preserves that snapshot by construction, which is what compliance audits require.

5. Three Retrieval Questions

The two time axes support three retrieval modes:

What is true at time T?

# Active records valid at day 2
mem.retrieve_valid_at(at=day2, subject="client:42")  # → "high"

This filters on the valid-time axis and only returns currently active records (those with open recorded_to). It reflects the corrected world-state.

What had the system recorded by time T?

# What was known by day 2?
mem.retrieve_known_at(at=day2, subject="client:42")  # → [] (nothing yet)

This filters on the record-time axis only. It answers “what information had arrived by this point?” without judging whether it was valid. Since the fact was not ingested until day 3, the result is empty.

What did the system believe at time T?

# Belief state: valid at day 2, known by day 4
mem.retrieve_belief_state(at_valid=day2, at_record=day4)  # → "medium"

# Same question, but known by day 6 (after correction)
mem.retrieve_belief_state(at_valid=day2, at_record=day6)  # → "high"

This is the intersection: facts that were both valid at at_valid and recorded by at_record. It reconstructs exactly what the agent would have believed at any past moment. The first query returns “medium” because the correction had not arrived by day 4; the second returns “high” because it had arrived by day 6.

6. History, Diff, and Timeline

Three more methods support auditing and debugging:

  • history(subject): all facts for a subject, including closed records, sorted by record time, showing the full correction chain.
  • diff_between(t1, t2, axis): facts present at t2 but not t1 on the specified axis, showing what changed between two points in time.
  • timeline_for(subject): all facts sorted by valid time, showing the world-time narrative including superseded records.
# Full correction history
mem.history("client:42")

# What changed on the record-time axis between day 4 and day 6?
mem.diff_between(day4, day6, axis="record")

# World-time narrative
mem.timeline_for("client:42")

7. Relationship to Existing Memory Systems

Operon already includes two other memory subsystems. BiTemporalMemory complements them; each handles a different kind of memory:

SystemTime ModelMutationUse Case
HistoneStore Single timestamp Mutable marks Epigenetic metadata on retrieval
EpisodicMemory Single timestamp Mutable (decay, promote) Tiered memory with relevance scoring
BiTemporalMemory Dual timestamps Append-only Auditable fact tracking with corrections

HistoneStore annotates retrievals with epigenetic marks (access frequency, recency, context). EpisodicMemory manages tiered decay and promotion between working, short-term, and long-term memory. Neither tracks corrections or supports dual-axis retrieval. BiTemporalMemory serves domains where keeping an audit trail of past beliefs matters.

10. What Comes Next

Bi-temporal memory is Phase 1 of the memory roadmap. The planned next pieces are causal event logging (recording why decisions were made alongside the facts available at the time), persistent storage backends so the append-only log survives process restarts, and temporal query primitives that let agents inspect their own epistemic history during planning.

If an agent cannot reconstruct what it believed when it acted, it is hard to trust with consequential decisions. Putting dual-axis history directly in the memory store builds auditability into the data model from the start.
