Phase C: The 8B Ceiling Holds Cross-Model, and Retry Is the Wrong Lever

22 hours on Ollama, 30 submissions on a second 8B model with format-correction retry enabled, and zero recoveries.
Bogdan Banu · April 18, 2026
operon-ai v0.35.0

Recap: three candidate fixes

The v0.34.5 post traced SWE-bench Phase 2’s failures to 8B diff-format discipline rather than file selection, and listed three candidate ways to improve the result:

  1. Stronger model. Most likely to change the result.
  2. Format-correction retry. Re-prompt on sanitizer rejection with the specific failure reason.
  3. LLM-localized candidate ranking. Likely marginal.

In v0.35.0, we tested a second locally available 8B model with --retry-on-reject enabled: deepseek-r1:8b (DeepSeek-R1 reasoning training distilled onto a Qwen3-8B base, Q4_K_M, 8.2B parameters). Since 8B models already sit below the SWE-bench-lite threshold, the goal was to check two things: whether the v0.34.5 ceiling generalizes across training regimes, and whether reason-coded retry prompts recover any sanitizer-rejected submissions.

The run

We ran the same 10 SWE-bench-lite instances and grounded prompt pipeline as v0.34.5 across the same three conditions (baseline, organism, langgraph). New in v0.35.0: whenever the sanitizer rejects a patch, the runner re-prompts the model once with the specific reason code (one of placeholder_hunk, truncated_hunk, overlong_hunk, path_not_found, ambiguous_path, empty_extraction, malformed_metadata), the failed output embedded verbatim, and guidance tailored to that failure mode. With _FORMAT_RETRY_MAX = 1, the retry fires at most once per instance per condition.

PR #57 raised the per-call LLM timeout from 120s to 900s so reasoning models’ long <think> blocks do not trip the OpenAI-compatible client’s default. PR #58 added the sanitizer’s tuple-return sanitize_with_reason(patch, slug, tree_paths), the _build_retry_prompt helper, runner-level retry callbacks for all three conditions, and the --output CLI flag so Phase C artifacts do not overwrite v0.34.5’s. Both PRs landed on main before the run started.

Total wall-clock time was ~22 hours. Reasoning models are slow: mean per-call latency was 18–19 minutes across all conditions, compared to gemma4’s 2–3 minutes in v0.34.5. The 900s timeout absorbed every call, leaving zero runtime errors in the artifact (the two astropy instances that hit the old 120s ceiling in v0.34.5 completed cleanly here).

Two main findings

1. The 8B ceiling holds across models

Both 8B models resolved zero instances. Gemma4 got one patch past the sanitizer; deepseek-r1 got none. The lone v0.34.5 “survivor” (django/django-11001 baseline, which still ended unresolved) turned out to be gemma4-specific. Deepseek-r1 could not produce a git apply-clean diff for that instance under any of the three conditions (baseline, organism, or langgraph).

In the v0.34.5 post, we hypothesized that the single survivor reflected a structural property of that issue (likely a small, localized hunk). Under that hypothesis, another 8B model should have been able to format a clean diff for django-11001 in baseline too. The cross-model data rules that out: the survivor was an idiosyncrasy of gemma4’s output distribution on that prompt. The 8B-class format-discipline ceiling generalizes beyond gemma4 to a reasoning-distilled 8B model.

2. Reason-coded retries did not break the ceiling

The retry path itself ran as intended: the callback fired on every rejection, each retry prompt embedded the reason code, the failed output verbatim, and reason-specific guidance (“use real integer line numbers” for placeholder_hunk, “use exact paths from the repository context” for path_not_found, and so on), and the v0.35 artifact records retry_attempted=true and retry_recovered=false on all 30 submissions.

The failure-reason distribution explains why. Across the 30 submissions, 26 were empty_extraction (the model’s output contained no diff-shaped content at all), 3 were overlong_hunk, and 1 was truncated_hunk. Zero submissions hit placeholder_hunk, path_not_found, or ambiguous_path; the grounding-specific rejections never fired, consistent with v0.34.5’s finding that file selection is not the bottleneck.

Retry cannot move a model across a capability boundary. At 8B, 26 of 30 failures occurred because the model produced no diff-shaped output in the first place, while only 4 produced a diff with fixable structural errors. Guided retry targets models that can already emit valid diffs and occasionally slip; deepseek-r1:8b rarely reached that point. Even the empty_extraction retry prompt (“respond with a single fenced diff block and nothing else”) failed to elicit diff-shaped output. Retry can recover lapses, but it cannot push a model past a format threshold it rarely clears on its own.

This is a sharper negative than the v0.34.5 post predicted. That post guessed retry “might recover 20–40% of sanitizer drops.” At 8B, it recovered 0 of 30. That 20–40% estimate assumed a model close to emitting valid patches, and neither gemma4 8B nor deepseek-r1 8B is close. For retry to justify its 2× cost, the base model needs to already produce valid patches some of the time, which likely means 70B+ or a stronger 30B-class model.

Scope of the result

Three conclusions follow from this run: (i) the 8B format-discipline ceiling holds across training regimes, with reasoning distillation showing no advantage over instruction tuning for diff format; (ii) targeted retry prompts do not recover failures when the base model lacks the underlying formatting capability; and (iii) the single v0.34.5 survivor was specific to gemma4 rather than an inherently easy issue. Confirming the ceiling on a second model architecture gives stronger evidence for its generality than another gemma4 rerun would have.

These results do not show that retry is useless at larger scales. For models close to producing valid unified diffs (likely 70B+ via Modal, Groq, or Together), the retry pipeline in v0.35 provides the right instrument to test recovery directly; we simply haven’t pointed it at that compute yet.

Nor does this null result weaken the structural guarantees of the categorical harness. Certificate preservation across compilers, priority gating, and stagnation detection are Know-level properties verified independently of SWE-bench task resolution.

Side observations

Repo-dependent latency

Astropy instances ran 25–30 minutes per call, whereas Django instances ran 6–15 minutes under the exact same model, grounded context injection, sanitizer, and retry setup. The difference tracks issue complexity: astropy’s stack traces reference more import paths and class hierarchies, producing longer <think> blocks. Reporting a single pooled average (“reasoning-model latency is ~18 min per call”) hides a 2× spread driven by repository structure rather than uniform reasoning effort.

The 900s timeout held

The v0.34.5 gemma4 run hit two baseline timeouts on astropy instances under the old 120s ceiling. Both completed cleanly here with the 900s timeout, with zero runtime errors despite 18-minute mean latencies. Raising a timeout originally sized for interactive callers is a basic correctness fix for extended-reasoning benchmarks.

Unused sanitizer reason codes

SANITIZE_REASONS defines eight reason codes; besides empty_extraction, this run logged overlong_hunk and truncated_hunk. The remaining codes (such as placeholder line numbers and basename-collision paths) are unit-tested but did not fire in live 8B data, where empty extraction, truncation, and overrun dominate. Larger models may shift that distribution: placeholder_hunk in particular shows up in models that reason about diff structure abstractly instead of grounding line numbers in real file content.

What’s next

  1. 70B+ cloud rerun. This is the obvious next step. Modal charges for GPU after its free tier, so Groq’s free-tier Llama-3.3-70B is a cheaper first pass using the same code, a different --model, and the same artifact writer. Any recoveries at 70B would provide the first positive signal for guided retry.
  2. Per-stage retry for organism. Currently a retry re-runs the whole organism. Re-running only the edit stage would halve retry cost and give a cleaner test of whether stage decomposition helps recovery. This is not yet shipped.
  3. Paper 4 / Paper 5 arXiv submission. With the §6.3 Phase C subsection in place, the Paper 5 claim is cross-model verified and ready for arXiv.

Summary

v0.35.0 ships Phase C: the retry pipeline that v0.34.5 proposed, a cross-model artifact confirming the 8B ceiling, and a null result on retries that sharpens the diagnosis. The headline score is unchanged (0 resolved on SWE-bench-lite), while the claim is narrower and better supported (cross-model, with retry active, zero recoveries). The harness is on PyPI and ready to run against 70B compute next.
