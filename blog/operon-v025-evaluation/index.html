Operon v0.25: The Compile–Decompile Loop

Comparing agent frameworks via a compile–decompile round-trip, and how Scion handles container isolation

Bogdan Banu · March 2026 · github.com/coredipper/operon

Release: v0.25.1
Abstract

The multi-agent ecosystem now includes at least six orchestration frameworks (Swarms, DeerFlow, AnimaWorks, Ralph, A-Evolve, and Scion), each built around a different coordination model. Operon v0.25 adds an evaluation harness to test whether structural guidance reduces risk across them. It works through a compile–decompile round-trip: compile an Operon organism into a framework’s native config, parse that config back through an adapter into a source-agnostic intermediate representation, and run Operon’s epistemic bounds on the result. Below are the round-trip mechanics, the synthetic and live evaluation results, and how Google’s Scion fits in through container-level isolation.

1. The Compile–Decompile Round-Trip

Comparing agent frameworks requires a shared representation. Their APIs are too different to unify directly, so the common ground has to be structural: how many agents exist, how they communicate, and what topology they form.

Operon v0.24 introduced ExternalTopology, a frozen dataclass that any framework’s config can be parsed into. v0.25 adds four compilers going in the opposite direction, from Operon’s internal representation out to each framework’s native format, forming a bidirectional pipeline: 

SkillOrganism
      ↓ compile
Framework Config  (Swarms dict, DeerFlow session, Ralph events, Scion grove)
      ↓ decompile
ExternalTopology  (source-agnostic IR)
      ↓ analyze
AdapterResult     (risk score, warnings, topology advice)
      ↓ derive
RunMetrics        (success probability, token cost, latency, interventions)

Compilation is lossy because each framework exposes different primitives. A Swarms SequentialWorkflow has no concept of cognitive modes, a Ralph hat config drops timeout values, and a DeerFlow session flattens stages into a skill list. The goal is to emit a valid native config for each target and measure which structural properties survive the round-trip.

The decompile step feeds that native config back through the same adapter used for handwritten framework configs. Because both inputs take the same code path, the analysis pipeline applies identical epistemic bounds and risk scoring whether a config was generated by Operon or written directly in Swarms.

What the Round-Trip Measures

Instead of asking subjectively which framework is better, the round-trip lets us test which framework preserves more topology information and whether that lowers the risk score. Both questions have measurable, reproducible answers.

2. Compilers and Adapters

Each compiler is a pure function (SkillOrganism → dict) with no framework imports and no side effects. It returns a plain, JSON-serializable dictionary matching what the target framework expects as input.

Compiler Output Format Key Mapping
organism_to_swarms() Swarms workflow config Stages → agents, order → edges, cognitive mode → GPT/Claude model tier
organism_to_deerflow() DeerFlow session config Lead stage → assistant, rest → sub-agents with skill lists
organism_to_ralph() Ralph hat config Stages → hats with event transitions, observational mode → backpressure gates
organism_to_scion() Scion grove config Stages → containerized agents with git worktree isolation + dedicated watcher

The six adapters go the other direction. Each takes a framework’s native config dict and returns an ExternalTopology: 

# Swarms round-trip
compiled = organism_to_swarms(organism)
topology = parse_swarm_topology(
    pattern_name=compiled["workflow_type"],
    agent_specs=compiled["agents"],
    edges=compiled["edges"],
)
result = analyze_external_topology(topology)
print(f"Risk score: {result.risk_score:.2f}")

Every adapter also has a *_to_stages() function that maps framework-native concepts back to Operon’s SkillStage list, enabling full bidirectional template exchange. A Swarms pattern discovered in production can be imported into Operon’s pattern library, analyzed, and re-exported to DeerFlow or Ralph.

3. The Evaluation Harness: Does Guidance Help?

The central question behind v0.25 is empirical: does Operon’s structural guidance actually reduce risk, or do agents self-organize effectively without it?

The evaluation harness answers this by running 20 benchmark tasks across 7 configurations. Each task has a difficulty tier (easy, medium, hard), a set of required agent roles, and an expected topology shape (sequential, parallel, or mixed). The configurations span guided and unguided deployments:

# Configuration Guided? Compiler
1 Operon adaptive Yes advise_topology + adaptive_skill_organism
2 Swarms auto No organism_to_swarms
3 DeerFlow default No organism_to_deerflow
4 AnimaWorks default No parse_animaworks_org
5 Ralph default No organism_to_ralph
6 Scion unguided No organism_to_scion (no watcher)
7 Scion + Operon Yes organism_to_scion + watcher

The MockEvaluator: Real Analysis, Synthetic Execution

The evaluator doesn’t call LLMs. Instead, it uses the compile–decompile round-trip to derive metrics from real structural analysis. For each task × config pair:

  1. Build a SkillOrganism from the task’s required roles
  2. If guided, run advise_topology(error_tolerance=0.01) to inform stage mode assignment
  3. Compile through the config’s compiler to a native dict
  4. Parse back through the adapter to ExternalTopology
  5. Run analyze_external_topology() to get the risk score
  6. Derive metrics: success probability = 1 − risk_score, token cost from stage count, latency from sequential overhead

Noise is deterministic: each task-config pair gets an RNG seeded with SHA-256(seed:task_id:config_id), so identical seeds produce identical results. The harness outputs ranking tables, per-config aggregate metrics with Wilson 95% confidence intervals, and structural variation summaries.

What the Live Evaluation Found

We ran the evaluation against real LLM providers: Gemini 2.0 Flash (API), Claude Code (CLI), and Codex (CLI). Guided multi-stage pipelines showed a consistent +6.2% quality improvement over unguided configurations, while single-agent CLI execution showed no effect, confirming that structural guidance only applies when there is a multi-node topology to shape. The compile→decompile round-trip also showed where structural information is lost: guidance sets stage mode assignments before compilation, and external compilers discard that metadata, producing identical topologies for guided and unguided configs.

Live Results: Three Providers, Four Tasks

We ran 4 benchmark tasks (3 easy sequential, 1 hard parallel) through guided and unguided configurations across three real providers. Guided configs use distinct fast/deep models (e.g. gemini-2.0-flash / gemini-2.5-flash); unguided use the same model for both nuclei.

Provider Config Success Quality Tokens Latency Risk
Gemini API unguided 25% 0.375 4,713 12.7s 0.170
Gemini API guided 38% 0.438 5,212 12.6s 0.170
Claude CLI unguided 0% 0.375 369 26.6s 0.050
Claude CLI guided 12% 0.438 350 24.2s 0.050
Codex CLI unguided 25% 0.625 156 31.8s 0.050
Codex CLI guided 25% 0.625 156 29.2s 0.050

Guidance effect. Gemini and Claude both gained +6.2% in quality with guidance, while Codex showed no difference because CLI providers execute as a single agent where multi-stage topology changes do not apply.

Provider choice outweighs topology on simple tasks. Codex reached the highest average quality (0.625) with the simplest topology, Gemini was fastest (12.7s), and Claude produced the top single-task score (1.00 on guided translation) while taking the longest (24–27s). On simple tasks the choice of model dominates, whereas on multi-stage pipelines structural guidance provides a consistent quality floor.

Risk scores track topology structure. Single-agent CLI runs receive risk = 0.050, while Gemini’s 2-stage sequential pipelines receive risk = 0.170 due to sequential error amplification. The score reflects the higher structural risk of multi-stage execution compared to a single node.

Credit Assignment

Beyond aggregate risk, the harness performs credit assignment, attributing run outcomes to individual stage contributions. Breaking the risk score down by stage makes structural bottlenecks visible, pinpointing the single agent whose error amplification dominates the topology’s risk profile.

4. Scion and Container Isolation

Google’s Scion takes a different starting point from in-process orchestrators like Swarms and DeerFlow. Its primary primitive is container isolation: each agent runs in its own Docker container with a dedicated git worktree and isolated credentials.

Scion’s philosophy is “less is more”: fewer agents, strict per-agent isolation, and minimal shared state. That sits at the opposite end of the design space from Swarms, which orchestrates dozens of lightweight agents inside one process. Each design optimizes for a different failure mode.

Scion vs. Swarms

Dimension Scion Swarms
Isolation model Container + git worktree per agent In-process, shared memory
Agent count preference Few, heavily isolated Many, lightweight
Communication Named message channels Direct function calls / edges
Failure mode optimized for Blast radius (one agent can’t corrupt another) Coordination overhead (minimize handoff latency)
Observability Dedicated watcher agent + OTEL telemetry Framework-level logging

Operon’s Scion compiler (organism_to_scion()) emits a “grove” config in which each stage becomes a containerized agent with git_worktree: true and credentials: "isolated". It also injects a dedicated operon-watcher agent for telemetry monitoring and convergence detection; the watcher is the only agent given shared credentials, since it has to observe the rest of the grove. 

# Scion compilation
from operon_ai.convergence import organism_to_scion

grove = organism_to_scion(organism, runtime="docker")

# Each stage agent gets:
# {
#   "name": "researcher",
#   "template": {"system_prompt": "...", "skills": [...]},
#   "runtime_profile": "medium",
#   "isolation": {
#     "git_worktree": True,
#     "credentials": "isolated"
#   }
# }

# Plus an injected watcher:
# {
#   "name": "operon-watcher",
#   "isolation": {"git_worktree": False, "credentials": "shared"}
# }

Combining Isolation with Structural Analysis

Comparing “Scion unguided” (config 6) against “Scion + Operon” (config 7) tests whether structural guidance changes the risk profile on top of container isolation. The two layers cover orthogonal failure modes:

  • Scion alone provides runtime isolation, so one agent’s crash or credential leak cannot propagate to another.
  • Operon on top adds static structural analysis, catching error amplification, sequential penalties, and topology mismatches before deployment.

A topology with a 6.4x error amplification bound will still compound mistakes across stages even when every agent sits in its own Docker container. Container isolation contains runtime cascades, while structural analysis flags logical cascades before the run starts.

5. Practical Implications

Framework authors get a free structural linter

Writing an adapter requires a single parse function. Once a framework emits an ExternalTopology, Operon’s epistemic layer computes error amplification bounds, sequential penalty estimates, tool density scores, and topology recommendations with no changes to the framework itself.

Template exchange becomes framework-portable

A coordination pattern discovered in Swarms can be imported into Operon’s PatternLibrary, scored against historical run records, and re-exported as a DeerFlow session, a Ralph hat config, or a Scion grove without tying the pattern to its original runtime.

Evaluation becomes apples-to-apples

Because every framework passes through the same compile–decompile pipeline, its risk score depends purely on the topology its compiler produces. If Framework A emits a deeper sequential chain than Framework B for the same task, the higher risk score reflects that chain depth directly.

The “less is more” hypothesis is testable

Scion favors a few heavily isolated agents, while Swarms favors many lightweight ones. With the evaluation harness, you can compile the same 20 tasks through both targets, decompile the outputs, and compare the resulting risk scores directly rather than arguing the trade-off in the abstract.

Orchestrators as Compilers

It helps to treat agent orchestration frameworks as compilers that map a task specification to a coordination topology. Under that view, Operon’s four compilers handle code generation, its six adapters handle decompilation, the analysis pipeline acts as a type checker, and the evaluation harness serves as the benchmark suite for the generated output.

6. Future Work: Prompt Optimization and Workflow Generation

v0.25 also introduces two protocol interfaces for capabilities that are not yet fully implemented but whose contracts are now stable:

  • PromptOptimizer: a @runtime_checkable Protocol for prompt-level tuning. The reference implementation (NoOpOptimizer) is a pass-through; EvolutionaryOptimizer defines the extended protocol for mutation-based optimization with fitness gating. attach_optimizer() wires any implementation into all stages of an organism.
  • WorkflowGenerator: a protocol for natural-language-to-topology generation. HeuristicGenerator provides rule-based workflow construction as a baseline; ReasoningGenerator defines the protocol for LLM-powered workflow synthesis. generate_and_register() integrates any generator with the PatternLibrary.

Both interfaces are defined as Python Protocols rather than abstract base classes, so any object with matching method signatures satisfies the contract without inheritance. DSPy optimizers, LangChain generators, or custom classes can plug in without importing Operon.
